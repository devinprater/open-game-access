# Fire Emblem: Shadow Dragon — reverse-engineering notes (FE11)

**Platform:** Nintendo DS · **Region:** USA · **Game code:** `YFEE` · **Revision:** 0

| | |
|---|---|
| Title (header) | `FIREEMBLEM11` |
| Maker code | `01` |
| Size | 67,108,864 bytes (64 MiB) |
| **SHA-1** | `7b7b307ef819ac31a7b71aed2e8e47ff23c1765e` |
| **SHA-256** | `bebe9ce0d727a61f1676dd8360e2d4fe7be936b9123e187f106c6cbd555714d7` |

⛔ **Every address in this document was measured against exactly the ROM above.**
Addresses and symbols differ across regions and revisions. A memory map without the
exact ROM it came from is a trap: fields land a few bytes out and nothing says why.
Reproduce the identity with `scripts/fe-identity.sh`.

This document is the human-readable record. Machine-readable findings for Open Game
Access to consume live in `reverse-engineering/fe11/symbols.json`.

## How to read the confidence levels

| Level | Means |
|---|---|
| **confirmed** | Two independent sources agree — typically the decompilation *and* a live read of the running game. Safe to build on. |
| **strongly inferred** | One good source plus consistent behaviour. Likely right; has not been cross-checked. |
| **tentative** | Plausible, fits observations, unverified. Do not depend on it. |
| **unknown** | Not established. Listed so the gap is visible rather than silently absent. |

A decompiler's suggestion is **not** evidence on its own. The fe11-us decompilation is
invaluable for *where to look*, but its struct headers have already been wrong in three
places in this work (see "Decompilation headers that were wrong"), so its field types
are treated as hints to test, not facts to copy.

## Global objects — confirmed

All addresses are ARM9/overlay BSS for `YFEE` rev 0. The `gMapStateManager` group lives
in **overlay ov000's** BSS and is only mapped while ov000 is loaded — reading it outside
a map produces `0x00000000`, which is not a memory-map error but a "no map loaded"
answer.

| Symbol | Address | Evidence |
|---|---|---|
| `gFE11Database` | `0x02197254` | decomp `symbols.txt`; live read gives a valid pointer |
| `gUnitList` | `0x021974D8` | **confirmed** — live: 1-based array, stride `0xA8` |
| `gForces` | `0x021974DC` | **confirmed** — live: array of 6 `Force` structs, `id == index` |
| `gMapStateManager` | `0x021E3328` | **confirmed** — live: valid only while ov000 is mapped |
| `gActionSt` | `0x021E3344` | decomp `overlays/ov000/symbols.txt`; holds `unk_34` (acting unit id), `xDecision`/`yDecision` |
| `gMapRenderState` | `0x021E34FC` | decomp `overlays/ov000/symbols.txt` |

Note `gUnitList` (`0x021974D8`) and `gForces` (`0x021974DC`) are 4 bytes apart: the unit
list's second word is a tail pointer that the force array begins immediately after. Do
not read one as the other.

## `struct Force` — confirmed

```c
struct Force {          // sizeof = 0x0C … but see the caveat below
    Unit* head;         // +0x00
    Unit* tail;         // +0x04
    s32   id;           // +0x08   <- faction / force identity
};
```

`gForces = new Force[6]` — an **array of structs**, not an array of pointers. Live reads
confirm `Force.id == array index` for all six entries.

⛔ **`sizeof(struct Force)` is not a safe stride.** The entries observed live sit `0xA8`
apart, i.e. one unit-record stride, not `0x0C`. The six entries are reached by index
arithmetic that works, but the struct is not tightly packed in the live array. Read
`Force.id` and trust `id == index`; do not compute a 7th entry from a `0x0C` stride.

### Faction values — confirmed

Derived from the decompilation's own indexing (`src/ov000/disposition.cpp`:
`Force::Get(faction + 2)` at :392/:405, `Force::Get(2)` at :471 for the player army) and
then confirmed against live data:

| `id` | Meaning | Live evidence |
|---|---|---|
| 0 | Player | Marth's army (Prologue: 1 unit) |
| 1 | Enemy | Prologue soldiers/fighters: 4 units |
| 2 | Player (scenario) | 9 units in the final-boss save |
| 3 | Enemy (scenario) | **22 units** in the final-boss save |
| 4 | Unassigned reserve | 60 units live — not on the map |
| 5 | Other | empty in every observation |

⛔ **Faction 4 holding ~60 units is normal, not a bug.** Those are roster slots with no
HP and position `(0,0)`. A reader that treats "has HP field" as "is on the map" will
report 60 phantom enemies. The correct test is position *and* the force id.

## `struct Unit` — confirmed

Stride **`0xA8`**, array base `gUnitList` at `0x021974D8`, **1-based** (`GetUnit(id) =
base + (id - 1)`).

| Offset | Field | Evidence |
|---|---|---|
| `+0x3C` | `next` (list link) | **confirmed** |
| `+0x40` | `pPersonData` | **confirmed** — deref gives `pid` string, e.g. `"PID_MARS"` |
| `+0x44` | `pJobData` | **confirmed** — deref gives `jid` string, e.g. `"JID_LORD"` |
| `+0x4C` | `force` (pointer to a `Force`) | **confirmed** — its `+0x08` reads the faction |
| `+0x6A` | level | confirmed |
| `+0x6C` | `hp` | **confirmed** — 18 for Marth at Prologue start |
| `+0x6D` | `mov` | confirmed (0 until deployed; use `JobData.mov` instead) |
| `+0x6E` | `xPos` | **confirmed** — tracks the cursor's tile |
| `+0x6F` | `yPos` | **confirmed** |
| `+0x70` | `items[5]` | confirmed |
| `+0x98` | `state1` | see the warning below |

### ⛔ `state1` does not mean what the decompilation guesses

The decompilation suggests bit flags for acted/dead. Filtering on those bits produced
**"0 live units" for a map with a full army on it.** The bits' real meaning is not
established. `US_ACTED = 1<<0` and `US_DEAD = 1<<3` are **tentative** at best.

### ⛔ Do not identify a unit by level and HP alone

Unused array slots read `level = 1, hp = 0, x = 0, y = 0` — which passes any naive
"level in range" check and produced phantom enemies such as *"Enemy 12, 0 HP, position
0, 0"*. A record with **no HP and no position** is an empty slot. Require a plausible
position as well.

### Identity resolution

`pPersonData` → `pid` (`"PID_MARS"`) and `pJobData` → `jid` (`"JID_LORD"`) are the
game's **own identifier strings**, read from RAM. Only the display mapping is ours
(`PID_MARS` → "Marth"), and anything unmapped falls back to the raw identifier, which is
honest and still identifies the unit.

## `struct JobData` — confirmed

| Offset | Field | Evidence |
|---|---|---|
| `+0x28` | `unk_28` — **movement type** (cost-matrix row) | **confirmed** — `u8`, live: Lord 0, Soldier 23, Fighter 7 |
| `+0x29` | `mov` — class movement stat | **confirmed** — live: **Lord 7, Soldier 6, Fighter 6** (the real FE values) |

⛔ **`unk_28` is a byte, not a pointer.** Reading it as a 32-bit value gives `50464512`
(`0x03025C00`) — which *looks* like an address and is really the byte plus three
neighbouring fields. This cost real time.

## Terrain and movement costs — confirmed

The game's own movement test, recovered verbatim from
`src/ov000/map_sequence.cpp:2741`:

```c
if (func_0203826c(
        gFE11Database->pTerrain[gMapStateManager->unk_828[ix | iy << 5]].unk_08,
        pUnitA->pJobData->unk_28) < 0)      // <0 == impassable for this movement type
    continue;

gMapStateManager->unk_08->unk_0854[ix | iy << 5] = 0;   // mark reachable
```

with these tiles skipped beforehand:

```c
unk_82c[ix | iy << 5] & 0x80            -> skip   // impassable flag
unk_d30[(ix|iy<<5) >> 3] & (1 << (ix&7)) -> skip  // reachability bitmap
GetUnit(unk_028[ix | iy << 5]) != NULL   -> skip  // tile occupied
```

### The cost matrix

Indexed **`[movementType][terrainCategory]`**, reached at `gFE11Database->unk_28`.

⛔ **`TerrainCostData` in `include/database.hpp` is wrong about one field.** It declares
`s8 * unk_04` — a *pointer*. The live bytes at `+4` are `01 01 01 FF`, i.e. costs
1, 1, 1, −1, not an address. `unk_04` is a **flexible array member**: cost rows begin at
`+4`, and `size` at `+0` is the row **width** (32 = the terrain-category count), not the
number of movement types. Reading it as a pointer is what made an early attempt conclude
the matrix was garbage.

Verified live — each class resolves a different row, with the real movement stats:

```
Marth    Lord     mov=7  row  0 : -1 1 1 1 2 2 2 2 5 4 -1 1 -1 1 -1 2
Soldier           mov=6  row 23 : -1 1 1 1 2 2 2 2 -1 -1 -1 1 -1 1 -1 2
Fighter           mov=6  row  7 : -1 1 1 1 2 2 2 2 -1 3 -1 1 -1 1 -1 2
```

Lord (row 0) has cost **5** in category 8 where Soldier/Fighter rows have `-1` — the
real distinction between a Lord's mobility and a common soldier's. `-1` = impassable;
1 = open ground/road; 2 = forest/hill; 3 = mountain; 4–5 = higher peaks.

Terrain categories present on the Prologue map:

| Category | Tiles |
|---|---|
| 0 | 656 |
| 8 | 91 |
| 13 | 150 (the tile under the cursor) |
| 14 | 126 |
| 22 | 1 |

### ⛔ The game has NO category→name table

This was searched and does not exist:

* `pTerrain[tile].unk_08` is a category **number**;
* `db.unk_24[category]` is **null**;
* the readable strings in `pTerrain[tile].unk_04` are **background graphic** names
  (`"BBG01"`, `"BBG02"`) — an art asset, not terrain.

So any human-readable terrain word is **ours**, and must be labelled as such. The words
in `Core/fe_access.cpp::terrainName()` are inferred from cost-matrix behaviour
(a category every movement type pays 1 for is open ground; one only some types can enter
is rough going) and are **tentative** until checked against what the game draws.

## Map state — confirmed

`gMapStateManager` (`0x021E3328`) → `+0x010` cursor:

| Offset | Field | Evidence |
|---|---|---|
| `+0x10` | pointer to cursor struct | confirmed |
| cursor `+0x08` | `xTile` | **confirmed** — tracks movement |
| cursor `+0x09` | `yTile` | **confirmed** |
| cursor `+0x0A`/`+0x0B` | `xDisplay`/`yDisplay` (pixels) | confirmed |
| `+0x24`..`+0x27` | map bounds (`x0,x1,y0,y1`) | **confirmed** — Prologue: x 1..15, y 1..22 |
| `+0x028` | occupying unit id per tile (32×32) | **confirmed** |
| `+0x828` | **pointer** to tile-id array (32×32, `0x400`) | **confirmed** |
| `+0x82C` | impassable flags per tile (`& 0x80`) | **confirmed** |
| `+0x830` | terrain category per tile (32×32) | **confirmed** |
| `+0xD30` | reachability bitmap, **inline `u8[0x80]`** | see below |

⛔ **`unk_d30` is inline, not a pointer.** Declared `u8 unk_d30[0x80]` while `unk_828`
next door genuinely *is* a pointer. Reading `unk_d30` with a 32-bit load returns the
first four bytes (`FFFFFFFF`) and misreads a bitmap as an address.

⛔ **The blue movement overlay is not resident.** All five `0x80` candidate buffers
(`unk_c30`, `unk_cb0`, `unk_d30`, `unk_db0`, `unk_e30`) were sampled across 1500 frames
and **none** ever held a range-like value — they read `0` or all-1024. The overlay only
exists while a move preview is on screen. A reader must therefore **compute** range from
the game's own data (cost matrix + `JobData.mov` + categories + occupancy) rather than
expect the overlay to be readable. Depending on the overlay makes the reader depend on
screen mode — which is exactly the "model the screen" failure this project exists to
avoid.

## Chapter / map identity — strongly inferred

`struct MapData` (`include/database.hpp`) with the map table at `gFE11Database->unk_18`:

```c
struct MapData {
    char* unk_00;   // "bmap###" or "arena###" — the map identifier
    char* unk_04;   // "MCT###"  — chapter text id
    ...
};
```

`GetMapDBIndex(pMap) = (pMap - gFE11Database->unk_18) / sizeof(MapData)`, and
`func_0203812c(pMap)` returns `HashTable::Get1(pMap->unk_04)` falling back to
`pMap->unk_00` — i.e. **the game's own map-name getter**, so names come from the game
rather than a hand-made table.

Live dump of the first entries (`sizeof(MapData)` observed as `0x1C`):

```
map[0] @0x02266248  unk_00="bmap000"  unk_04="MCT000"
map[1] @0x02266264  unk_00=?          unk_04="bmap001"
map[7] @0x0226630C  unk_00="MCT006"   unk_04=?
```

The entries clearly are not uniform reads yet — `unk_00`/`unk_04` swap between rows, so
either the stride or the field order assumption is off for some entries.
**Which entry is the *current* map was not located.** This is an open problem. The
candidate approach is to find which `MapStateManager` field points into the map table,
since `GetMapDBIndex` is exactly `(pMap - table) / stride`.

## Text / dialogue — unknown

**Dialogue has not been located, in RAM or in the ROM.**

What *was* found in RAM: real message-table identifiers and asset filenames.

```
table @0x0221824C   gop_001  gop_002  gop_003  ill_203
table @0x022667C4   MG_ARITEA  MG_AKANEIA  MG_MACEDONIA  MG_GRUNIA   (nation names)
table @0x0226D564   MTUTH_00  MTUTH_05B  MTUTH_05T  MTUTH_06  MTUTH_08B
```

and asset names such as `startup.cmb`, `panel.cl`, `unitselect.sc`, `touchcursor.tpl`.

⛔ **These are IDs, not prose.** They index a message system; the actual dialogue text
was not found.

The ROM was searched for prose directly and **none was found**: `strings -n 32` yields
only leftover Nintendo Wi-Fi/SSL strings (`"The connection has already been
disconnected."`, VeriSign/Thawte certificate banners) — not game dialogue. The string
`MTUTH` does not appear in the ROM at all, despite RAM pointing at `MTUTH_*`, which
means the table is built at runtime or the text is compressed/encoded in a way a plain
ASCII scan cannot see. **This is an open problem, not a finished item.**

## Decompilation headers that were wrong

Recorded because each one cost real time, and because it establishes *why* fe11-us
header types are treated as hints rather than facts.

| Header claim | Reality | Symptom when taken at face value |
|---|---|---|
| `TerrainCostData.unk_04` is `s8*` | flexible array at `+4` | matrix looked like garbage |
| `JobData.unk_28` read as a word | it is a `u8` | got `0x03025C00`, "an address" |
| `MapStateManager.unk_d30` "a pointer" | inline `u8[0x80]` | got `FFFFFFFF` |
| `Unit.state1` acted/dead bits | meaning unestablished | "0 live units" on a full map |

## Method notes

**Suspect a modal dialog before suspecting the memory map.** Enemies never appeared for
tens of thousands of frames during the Prologue tutorial, and the faction census sat at
`player=1 enemy=0` — which read as "this map has no enemies" when it actually meant
*"the game is not advancing at all."* A tutorial popup was swallowing every button
press. The popup's own text held the fix: *"press B … to cancel the move."* When input
does not change game state, look for something intercepting the input first.

**Read the value where it lives, in the frame it is live.** `gMapStateManager` is
overlay BSS, mapped only while ov000 is loaded, so a read after the frame loop returns
`0` and says nothing about the terrain. The read must happen inside the frame loop.

**`poke_set_button`, not `poke_set_hotkey`.** `poke_set_hotkey` sends the accessibility
script's *letter* keys (J/K/L…), not DS buttons. A plan driven with `set_hotkey` never
moved anything — the run stayed on the title screen and `gMapStateManager` read
`00000000` for its whole length. This presents as a memory-map failure and is not one.

**Watch the shell boundary.** Building `PA_SHIM` as a one-liner through `wsl.exe` from
Windows breaks on the space in `Devin Prater`, and the failure surfaces much later as
`main.lua:3: attempt to index a nil value (global 'emu')` — which reads like a broken
script. Use script files; they avoid the whole class of error.
